# Codefield: mobile-first, voice-powered coding — implementation brief

## Copy-ready implementation prompt

You are working on Codefield 0.4.0-alpha. Start from `release/codefield-0.4.0-alpha` and inspect its code and tests before changing behavior. Build the features below as integrated, production-minded increments, retaining the existing local-first experience and full playground editor. Use the accompanying backlog for ordering and acceptance criteria. Do not present planned functionality as already shipped.

**Vision:** Make coding and problem solving on a phone, or on a computer using only voice, powerful and practical enough to complete an entire coding session. Voice should be an optional, first-class interface, with clear feedback and a full touch/keyboard fallback.

1. **The full Codefield editor everywhere.** Give every code-editing surface—including LeetCode practice, lessons, checkpoints, notebooks, comparison views and floating views—the same core playground capabilities. Inventory actual differences and close them; sharing `createEditor` alone is not sufficient. Preserve independent drafts, problem context and appropriate layout. Adapt controls to small screens without hiding essential capabilities.
2. **Automatic Rust and C++ execution (priority).** Offer opt-in, debounced execution after edits using a suitable local compiler or an explicitly authorized remote backend. Reuse existing snippet wrappers where applicable. Explain where source is sent, and display compilation errors, cancellation, rate limits and service unavailability. Cancel or supersede stale work and prevent responses from overwriting newer results. Never silently transmit code. Explicit Run must remain available.
3. **Live Trace in practice for every supported language:** JavaScript, Ruby, Python, Rust, C++ and C#. Trace actual execution of the selected example, with input, source locations, variable changes, output, result and errors where supported. Include Rust. Provide accurate source mapping for generated wrappers, bounds on time/events/output and explicit capability/error states; do not label static guesses as runtime values. Build adapters and a shared event model; prove each language on real examples. If a construct cannot be traced, say so rather than invent values. Support user-supplied input when example adaptation is unavailable.
4. **Voice-only coding workspace.** Add a dedicated mode accessible from the main navigation. Allow a user to create/open code, navigate, dictate, edit, select, undo/redo, run, inspect results, and switch language without a keyboard. Show the recognized transcript, intended action and selection; provide optional spoken feedback, help, and a reliable stop/mute control. A user must be able to recover from recognition errors. Keep audio and transcript handling transparent and avoid recording when the microphone is off.
5. **Deterministic, no-LLM voice commands.** Interpret commands locally with a documented grammar and contextual language-aware lexing. For example, `highlight tally` selects an unambiguous matching identifier or method near the cursor; `highlight back 3` selects the previous three word tokens. Disambiguate multiple matches, respect code boundaries and preserve undo/redo. Recognize programming context such as a spoken `dot` followed by a method name, and support punctuation, casing, identifiers and literal dictation. An LLM must not be required to interpret or execute commands; disclose if the speech-to-text engine itself needs network access. Never execute a destructive or ambiguous action without an explicit confirmation mechanism.
6. **Harder follow-ups.** After a verified solve, offer curated, testable extra constraints for many supported problems. Each variation needs a clear statement, valid examples and an independent checker or reference oracle. Keep original progress and solutions separate. Generated suggestions may be shown as unverified ideas but cannot be presented as checked challenges without validation. Show an honest fallback when no verified variation exists.
7. **Structured problem paths.** Offer curated roadmaps for arrays, strings and other common topics, with ordered steps, prerequisites, progress, next problem and random eligible problem. Preserve random filters, avoid immediate repeats where possible, and handle unavailable or account-gated problems clearly. A user can continue a path or browse freely; persist progress locally.
8. **Mobile-first workflow.** Design for narrow viewports, touch selection, soft keyboards, safe areas, screen readers, orientation changes and flaky connectivity. Keep the editor, run/trace controls, problem statement and voice controls reachable without losing state. Validate on real mobile browsers as well as desktop.

## Engineering instructions

- First map feature and language support in the existing build, then implement the shared contracts and ship thin vertical slices. Preserve current behavior and data, including drafts and explicit runs.
- Separate speech recognition from deterministic intent parsing and editor actions; make recognition an adapter so it can be replaced or mocked. Do not promise offline recognition without a tested local engine.
- Separate execution and tracing behind adapters with consistent cancellation, resource budgets and provenance. External compiler services may have restrictions or change; verify suitability and configuration before use. Prefer a viable local execution path when available; remote auto-run must be an informed opt-in.
- Design voice interactions for ambiguity, noisy recognition, accents and accessibility. Make destructive edits reversible or explicitly confirmed. Do not execute arbitrary dictated shell commands.
- Use meaningful automated tests for commands, editor parity, runners, trace correctness, persistence, variations and paths. Add end-to-end checks and document manual phone, microphone and assistive-technology coverage. Test actual language runtimes and report any unavailable environments honestly.
- Update documentation, capability tables and release notes to match observed behavior. Do not ship the release until tests and applicable manual checks pass. Report completed work, remaining gaps and exact validation.

## Current baseline, verified from the supplied build

- `app/app.js`, `app/practice.js`, `app/learn.js`, `app/notebook.js` and `app/studio.js` already use the shared `src/editor.js`; feature integrations still differ.
- Rust and C++ have explicit remote program execution; the playground disables live preview when switching to those languages. Source is sent to Rust Playground or Compiler Explorer on explicit Run.
- Practice Live Trace is JavaScript-only and currently instruments a limited set of assignments on the first example. Do not confuse it with the static Code Map.
- Practice example checking has limited language and problem-shape support. General all-language tracing and verified constraints require additional harness work.
- README documents local browser storage and warns that browser workers are not a security boundary. Preserve and accurately describe those limits.

## Definition of done

A user can complete a representative practice session with the full editor on a phone, create and revise code by voice, run and inspect it, and continue a topic path. A test matrix demonstrates trace and execution for all six supported languages, including Rust and C++. Verified variations have independently tested oracles. Documentation states exactly what works, any service dependency and any remaining limitations. No existing release is overwritten or represented as containing unimplemented features.
